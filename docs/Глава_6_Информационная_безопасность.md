# 6 Анализ информационной безопасности приложения

Одним из ключевых приоритетов при разработке мобильного приложения **«Учёт посещаемости»** выступает защита персональных и учебных данных: ФИО студентов и преподавателей, номера билетов, журнал посещаемости, расписание, привязки NFC-меток к аудиториям. Система обрабатывает информацию, относящуюся к внутреннему контуру учебного заведения, поэтому требуется многоуровневая защита от несанкционированного доступа, подмены отметок и утечек учётных данных.

В процессе проектирования были учтены следующие направления:

- **конфиденциальность** — пароли не хранятся в открытом виде; обмен клиента и сервера выполняется по HTTP(S) в формате JSON;
- **аутентификация и сессии** — вход по билету (логину) и паролю, выдача серверного токена сессии, возможность выхода с инвалидацией токена на сервере;
- **авторизация (RBAC)** — разделение прав студента, преподавателя и администратора на уровне API и интерфейса;
- **целостность учёта посещаемости** — NFC-сессия преподавателя, проверка метки аудитории и принадлежности студента к группе занятия;
- **сопровождение** — смена пароля, заявки на восстановление доступа, сброс пароля администратором и по SMS-коду (демо-контур).

Политика обновлений предполагает регулярное обновление зависимостей (Ktor, Exposed, Compose) и устранение уязвимостей в серверной и клиентской частях. Для промышленной эксплуатации рекомендуется развёртывание сервера за **HTTPS**, ограничение CORS доверенными origin и переход с демо-токенов на **JWT** (в проекте подключены модули `ktor-server-auth-jwt`).

Реализация мер безопасности опирается на:

- криптографически стойкое хеширование паролей (**BCrypt**);
- проверку роли на сервере при каждом чувствительном запросе;
- разграничение UI по роли в клиенте (Compose);
- журналирование HTTP-запросов на сервере (`CallLogging`);
- перспективу MFA (биометрия устройства + пароль) и расширенного аудита действий администратора.

## 6.1 Защита пользовательских данных

### 6.1.1 Хранение паролей

Хеш-функция — отображение \(h = H(M)\), где \(M\) — пароль пользователя, а \(h\) — строка фиксированного формата, по которой **невозможно** восстановить исходный пароль. В проекте для хранения паролей в таблице `users` (поле `password_hash`) применяется алгоритм **BCrypt** (библиотека jBCrypt, 10 раундов — аналог `saltRounds = 10` в методических примерах).

Центральная реализация — объект `PasswordHasher` (листинг 6.1).

```kotlin
object PasswordHasher {
    private const val BCRYPT_ROUNDS = 10

    fun hash(raw: String): String =
        BCrypt.hashpw(raw, BCrypt.gensalt(BCRYPT_ROUNDS))

    fun verify(storedHash: String, rawPassword: String): Boolean {
        if (storedHash.isBlank()) return false
        return if (isBcryptHash(storedHash)) {
            BCrypt.checkpw(rawPassword, storedHash)
        } else {
            legacySha256Hex(rawPassword) == storedHash
        }
    }
}
```

**Листинг 6.1 – Хеширование и проверка пароля (фрагмент `PasswordHasher.kt`)**

BCrypt выполняет:

1. **Генерацию соли** — уникальной для каждого пароля, встраивается в строку хеша (`$2a$10$...`).
2. **Настройку сложности** — параметр `BCRYPT_ROUNDS = 10` увеличивает время подбора пароля перебором.
3. **Одностороннее преобразование** на базе шифра Blowfish — стойкость к восстановлению пароля из БД.

**Преимущества BCrypt в контексте дипломного проекта:**

- пароль в БД никогда не хранится в открытом виде;
- при компрометации дампа БД злоумышленник получает только хеши;
- при входе выполняется `BCrypt.checkpw`, а не сравнение с «голым» паролем.

Для совместимости с ранее созданными демо-записями предусмотрена проверка устаревших хешей **SHA-256** и **автоматическое обновление** до BCrypt после успешного входа (`DbAuthRepository.login`).

### 6.1.2 Аутентификация и сессии

**Регистрация студента** (`POST /auth/register`): билет из 7 цифр, пароль не короче 4 символов (для продакшена рекомендуется политика сложности 8+ символов), запись в `UsersTable` с ролью `STUDENT`.

**Вход** (`POST /auth/login`): сервер находит пользователя по `student_ticket`, проверяет пароль через `PasswordHasher.verify`, возвращает `AuthResponse` с полем `token` и данными пользователя (роль, ФИО).

**Сессия:** токен выдаётся компонентом `DevSessionRegistry` (формат `dev-{userId}-{UUID}`). При повторном входе предыдущий токен пользователя **отзывается**. **Выход** (`POST /auth/logout`) инвалидирует токен на сервере — повторное использование отклоняется (покрыто автотестом `authLogoutInvalidatesSession`).

**Смена пароля** (`POST /auth/password`): проверка старого пароля через `verify`, сохранение нового через `hash`.

**Восстановление доступа:**

- заявка администратору (`POST /auth/forgot-password`, таблица `password_reset_requests`);
- сброс по SMS-коду (`/auth/password-reset/phone/start`, `/auth/password-reset/phone/confirm`) с ограниченным временем жизни кода (`PasswordResetCodeRegistry`).

Клиент (модуль `shared`, `AuthViewModel`) хранит `AuthResponse` в оперативной памяти на время сеанса; при выходе состояние очищается и токен отзывается на сервере.

### 6.1.3 Передача данных

Клиент обращается к REST API сервера Ktor (`AttendanceRepository`, Ktor Client) с заголовком `Content-Type: application/json`. В учебной и локальной среде используется HTTP; **для эксплуатации в сети вуза** необходимо TLS (HTTPS) и запрет передачи паролей по незащищённым каналам Wi‑Fi.

Чувствительные операции (журнал, админ-каталог, NFC-отметка) передают **билет пользователя** в пути или теле запроса; сервер повторно проверяет роль в БД, а не доверяет только данным из клиента.

### 6.1.4 Защита сценария NFC-посещаемости

Отметка присутствия (`POST /attendance/nfc/mark`) дополнительно опирается на:

- активную **сессию преподавателя** (`AttendanceSessionsTable`, срок действия);
- идентификацию студента по **персональной NFC-карте** (`nfc_tokens`) **или** по метке **аудитории** (`rooms.nfc_uid`) с передачей `studentTicket` в теле запроса;
- проверку принадлежности студента к **группе занятия** (`resolveLessonForStudentGroup`).

Это снижает риск удалённой подстановки «чужой» отметки без физического присутствия у метки и без открытой сессии на паре.

## 6.2 Ограничение прав доступа пользователей

В приложении реализована модель **RBAC** (Role-Based Access Control) с **тремя ролями**, зафиксированными в `UserRole`: `STUDENT`, `TEACHER`, `ADMIN`. Роль хранится в `users.role` и возвращается клиенту при входе; интерфейс и API используют её для разграничения функций.

**Таблица 6.1 – Роли и полномочия**

| Роль | Обозначение | Основные действия | Ограничения |
|------|-------------|-------------------|-------------|
| **Студент** | `STUDENT` | Расписание своей группы, календарь, профиль, просмотр посещаемости, NFC-подтверждение на активной сессии, уведомления | Нет доступа к журналу других групп, админ-центру, открытию NFC-сессии |
| **Преподаватель** | `TEACHER` | Расписание своих пар, журнал посещаемости групп, открытие/закрытие NFC-сессии, отметка студентов, запрос переноса занятия | Не управляет справочниками вуза, не подтверждает заявки администратора |
| **Администратор** | `ADMIN` | Каталог групп, курсов, студентов, преподавателей, аудиторий, привязка NFC к комнатам, обработка заявок на сброс пароля, расписание всех групп, решения по переносам | Не подменяет роль преподавателя на паре без соответствующей учётной записи |

### 6.2.1 Контроль на сервере

Проверка прав выполняется **на сервере** при обработке запроса, например:

- `AdminScheduleService.requireAdmin` — доступ к операциям расписания и переносов только для `ADMIN`;
- `AttendanceService` — старт/стоп NFC-сессии только для учётной записи преподавателя, ведущего пару;
- `WeekScheduleService` — выборка занятий зависит от роли (студент — своя группа, преподаватель — свои курсы, админ — расширенный обзор);
- `markByNfc` — отказ при неверной метке, чужой группе или закрытой сессии.

Попытка вызова админ-метода с билетом студента или преподавателя приводит к пустому результату или HTTP 400/403 — **принцип минимальных привилегий**.

### 6.2.2 Контроль в клиенте

В модуле `composeApp` навигация и экраны зависят от `UserRole`:

- студенту недоступны админ-центр и журнал преподавателя;
- преподавателю показывается NFC-режим «преподаватель» и журнал групп;
- администратору — `AdminCenterScreen`, привязка NFC к аудиториям, обработка заявок.

Клиентское скрытие кнопок **не заменяет** серверную проверку, а лишь улучшает UX и снижает число ошибочных запросов.

### 6.2.3 Учётные записи и активность

- Поле `users.is_active` позволяет отключать доступ без удаления истории.
- Студент регистрируется только при наличии билета в справочнике (логика регистрации в `DbAuthRepository`).
- Преподаватели из справочника `teacher_directory` синхронизируются в `UsersTable` с ролью `TEACHER` (`TeacherDirectoryAccountSync`).

**Перспективы развития RBAC:** журнал аудита действий администратора, временные роли, разграничение прав деканата и методиста, интеграция JWT с claim `role`.

## 6.3 Вывод по разделу

В ходе анализа информационной безопасности приложения «Учёт посещаемости» внедрён комплекс мер, соответствующий специфике учебного мобильного сервиса.

**Защита учётных данных:** пароли хранятся в виде хешей **BCrypt** с солью и настраиваемой сложностью; реализованы смена пароля, выход с отзывом сессии и каналы восстановления доступа через администратора и SMS-код.

**Разграничение доступа:** модель **RBAC** с ролями студент, преподаватель и администратор реализована на уровне базы данных, REST API и пользовательского интерфейса; чувствительные операции журнала, расписания и NFC-сессий привязаны к роли и идентификатору пользователя на сервере.

**Целостность посещаемости:** NFC-сценарий дополняет парольную аутентификацию физическим фактором (метка аудитории / карта) и логикой активной сессии преподавателя.

**Ограничения дипломной версии** (зоны дальнейшего усиления): обязательный HTTPS в продакшене, усиление политики паролей, полноценный JWT вместо демо-токена, сужение CORS, MFA (биометрия Android + пароль), централизованный аудит-лог админ-действий.

Реализованные решения соответствуют базовым требованиям защиты персональных и учебных данных и создают основу для масштабирования безопасности при внедрении системы в учебное заведение.
